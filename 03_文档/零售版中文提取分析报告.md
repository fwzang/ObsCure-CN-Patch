## 一、核心结论（★★★）

### 1. 官方简体中文是【位图预渲染】，不是文本

这是本次分析最重要的发现，也解释了此前所有检索为何失败。

零售版的 `_en` 后缀贴图**直接把简体中文烧录进像素**。实例：

| 文件 | 官方中文标题（读自像素） |
|---|---|
| `pmapb1_en.bmp` | 行政楼 三层 |
| `pmapb0_en.bmp` | 行政楼 二层 |
| `pmapb2_en.bmp` | 行政楼 阁楼 |
| `pmapb3_en.bmp` | 行政楼 一层 |
| `pmap12_en.bmp` | 教室 二层 |
| `mplayb1_en.bmp` | 学校纪录（姓名栏为手写体中文：姓名 / 物品及钱 / 物品及袋 / 雨伞及袋） |

**推论**：中文在游戏里**从未以 GBK / Big5 / UTF-16 等编码文本形式存在过**。
任何编码探测手段都不可能找到它 —— 这不是技术能力问题，是数据形态问题。

### 2. 语言文件 `en.lng` 已完整提取，但零中文

| 项目 | 数值 |
|---|---|
| 解出大小 | 116,280 字节 |
| 记录总数 | **3,070 条** |
| type=0（8-bit ASCII） | 301 条 |
| type=1（UTF-16LE 宽字符） | 2,769 条 |
| **含汉字的记录** | **0 条** |

`en.lng` 里的内容是：
- 英文按键名：`F1`…`F12`、`NumLock`、`A`…`Z`、`Num 0`…`Num 9`
- 测试短语：`Phrase test number 2`、`Mortifilia`
- 资源路径（宽字符）：`Wave_Bank`、`Video`、`res/...` 等

**结论**：用户此前的猜测「中文优先 en，考虑毕竟是英文文本为主」方向正确 —— 中文确实在 `en` 槽位，
但**不是 `en.lng` 这个文件**，而是它引用的那批位图。

## 二、用户疑虑的验证：「CD 文件有加密，可能存在无效文件」

### 结论：该疑虑对大数据包不成立

用户提出的这条线索是对的，但排查结果是**误判** —— 之前统计出的「647 个条目不可解压」
并非加密，而是我的长度字段读法有误。

### 真相：纹理类条目的压缩长度不来自目录字段

- HVP 普通条目：压缩长在 `meta[11:13]`（BE u16），数据偏移在 `meta[21:25]`（BE u32）
- **纹理类条目例外**：`meta[11:13]` 存的是**像素宽度**（如 256、512），不是压缩长度
- **真实压缩长 = 下一条目的 off − 本条目的 off**

修正后重新全量解压：

```
唯一有效条目 = 1469
解压成功     = 1463
失败         = 6    ← 全部是目录表区的伪条目（off=0x25 等），非真实资源
```

### 加密的正面反证

`OBSCURE.MSI`（InstallShield 安装数据库）中：

```
偏移 0x363006:  ProductLanguage  2052        ← 2052 = zh-CN（简体中文）
                 ÕýÔÚ¼ÆËã¿Õ¼äÐèÇó        ← GBK 解码 = "正在复制文件："
```

这是**中文本地化的 MSI 元数据**，证明该零售版确实是简体中文版，且安装数据未加密。
（注意：这里的 GBK 中文是**安装器界面文案**，不是游戏文本。）

## 三、技术突破记录

### ★ 突破 1：MSZIP 跨块字典解压（卡了两天）

InstallShield 使用的 MSZIP 变体在 32KB 块边界**不重置 LZ77 字典**，
后续块引用前块数据，导致标准 `zlib.decompress` 报 `invalid distance too far back`。

**根因定位**：CFFOLDER 表起点是 **47**，不是标准 MSCF 规定的 36 —— InstallShield 插入了 11 字节。
这导致之前解析出的 `coffCabStart` 读成了 ASCII `"Data"`，从而误判。

**解法**（`hvp_tools/cab3.py`、`hvp_tools/cabrun.py`）：
1. CFFOLDER 表暴力定位：用「coffCabStart < 文件大小、cCFData < 100万、typeCompress ≤ 4」筛选起点
2. 用 CFDATA 链式校验（从 coffCabStart 逐块累加 `8 + cbData`，看是否正好走到文件尾）确认解析正确
3. 字典注入：Python 的 zlib 模块不暴露 `inflateSetDictionary`，改为**构造 raw-deflate 的 stored 前缀**
   承载前 32KB 字典，再与目标块拼接成单流一次 inflate

**成果**：

| CAB | folder | CFDATA 块数 | 解压结果 |
|---|---|---|---|
| Data3.cab | folder1（`strmpack_pc.hvp`） | 15,433 | **15,433 / 15,433 = 100% 成功**，505,580,462 字节 |
| Data3.cab | folder2 | 15 | 15 / 15 成功，462,131 字节 |
| Data2.cab | folder1–7 | 8,489 合计 | 全部成功 |

### ★ 突破 2：组条目的「描述下一个资源」规则

`en.lng` 的目录项在位置 `0x103A7`，但它自身 meta 长度算出为 0（是目录表最后一项），
标准字段完全对不上。**解法**：根据此前逆向已确认的规则 ——

> **目录项 N 的 meta 实际描述的是「下一个资源」**

前一目录项是 `cin71.sub`，其 meta 长度 48 字节，内嵌字符串 `_texts`，
尾部 u32 = `0x25D109D5` → 正解为 `en.lng` 数据偏移，zlib 解出 116,280 字节。

### ★ 突破 3：语言文件结构完整解析

```
24 字节文件头
第 1..N-1 条: [u16 BE len][body: len 字节][meta: 6 字节]
最后一条:     [u16 BE len][body: len 字节]      ← 无 meta
body[0] = 类型: 0 = 8-bit ASCII,  1 = UTF-16LE 宽字符
meta = 6 字节，原样保留
```

按此规则解析 3,070 条，消耗字节数与文件大小**完全吻合（剩余 0 字节）**，结构确证正确。
