## 一、决定性发现：`watchdog_swap` 在本 build 里是**死代码**

来源：`C:\Users\fwzang\ghidra_proj2\decomp_out\func_10006270.txt`（Ghidra 反编译 + 指令清单）

### 指令级事实（不是推测）

```
0x10006270  MOVD XMM0, ECX            ; this
0x10006274  MOVD XMM1, [0x100419C4]   ; g_orig_SetTexture
0x10006280  MOVD XMM1, [0x10041A70]   ; g_bigTex
0x10006288  MOVD XMM2, [0x10041A74]   ; g_fontTex
0x10006298  PXOR XMM0,XMM0 / PCMPEQD  ; 逐个比较 == 0
0x100062A0  MOVMSKPS EAX,XMM0
0x100062A3  TEST EAX,EAX
0x100062A5  JZ  0x100062A8            ; 四者都非 0 才继续
0x100062A7  RET                       ; 任一为 0 -> 直接返回
...
0x100062D2  CMP dword [0x10041A74],0  ; fontTex == 0 ?
0x100062D9  JZ  0x100063E1            ;   -> 换绑分支（SetTexture(bigTex)+apply_params_fast）
                                        ;   但门禁已保证 fontTex != 0 => 这条分支【永不可达】
```

**结论**：门禁要求 `g_fontTex != 0`，而唯一会执行
`SetTexture(this,0,bigTex) → apply_params_fast()` 的分支却写成 `g_fontTex == 0` 才进入。
=> **该分支是死代码；`watchdog_swap` 在正常运行时只做日志，不做任何纹理/参数动作。**

### 这条事实一次性解释了此前所有现象

| 现象 | 解释 |
|---|---|
| 文字要等**几秒**才出现 | 替换只由 `SetTexture` 钩子在"引擎第一次绑字体纹理"时触发；引擎没画文字前不会绑 |
| **图集糊墙**（图集跟着显现消失） | 换绑之后**没有任何还原路径**（看门狗是死的，c44 的帧末还原被 c45 删空）；残留 stage0=bigTex 被"陈旧缓存绘制"采样 |
| 我做的 v5（委托 watchdog）毫无效果 | 因为调的是一个死函数——等于什么都没做 |
| v4（自己判断+换纹理）文字全丢 | 只换纹理没补参数，UV 按 128 归一化采样 4096 高图集 → 采空白 |

## 二、三条路线的静态排查结果

### 路线 1：围绕 `exe+0x1EFCCE` 上扒 → **前提不成立，此路作废**

- `exe` 的 ImageBase = `0x400000`，所以该偏移对应 VA `0x5EFCCE`、文件偏移 `0x1EF0CE`
- 该处字节 `66 0f 54 c7 f2 0f 58 c2 ...`，反汇编显示它落在 **SSE 指令中间**
  （`movlpd xmm0,[0x65D4F8]` 覆盖 `0x5EFCC8–0x5EFCCF`）
- => **`0x1EFCCE` 不可能是本机这份 exe 的合法返回地址**，无法作为入口

补充排查（换个方法找"文字绘制批次"）：

- 全量反汇编 `.text`（814,691 条指令，`skipdata` 模式）
- 统计所有 `call [mem+disp]`：**0 条** 命中 D3D9 vtable 偏移
  （Clear=0xAC / GetTexture=0x100 / SetTexture=0x104 / DrawPrimitive=0x144 / DIP=0x148）
- 再统计所有指令的内存操作数：`0x104` 有 240 处、`0x100` 有 123 处，
  但逐一抽看全是**普通结构体字段**（如 `mov [ebx+0x104],edx` / `cmp [esi+0x104],0`），
  不能区分"vtable 槽"与"结构体字段"——**纯模式匹配在这份二进制上不可判**

**判定**：需要真正的反汇编器（Ghidra/IDA + 数据流/交叉引用）才能定位绘制批次。
本机现状：Ghidra **项目**在（`ghidra_proj2`，含 hook DLL 的反编译输出），
但 **Ghidra 程序本体与 Java 都不在**（`java`/`javac` 均无），无法新建 exe 的分析库。

### 路线 2：引擎是否自带"纹理缓存池" → **已由源码实证，静态不可枚举**

`version_proxy.c` 里有作者当年的实测记录（不是我的推断）：

- `:2069`「游戏会**反复重建**字体图集（指针每次都变，实测 10+ 次）」
- `:834-838`「游戏的"**陈旧缓存绘制**"（不再重新绑定纹理的那些 draw）」
- `:2452`「游戏反复重建图集（c44：10+ 次），旧指针会被 d3d9 堆重用给…」

=> 引擎确有缓存/复用行为，且**"不重绑就用陈旧 stage0"是客观存在的绘制模式**。
但这只能说明现象，**无法静态枚举出池子结构**——需要运行时日志或符号化数据流。

### 路线 3：字体对象结构与"复制独立中文对象" → **布局已知，但无法定位/改写持有者**

由 hook 侧逆向得到的对象布局（`version_proxy.c:1530-1540` 的写字段代码）：

| 偏移 | 含义 | 证据 |
|---|---|---|
| +0 | 字形表指针 | `*(DWORD*)(obj+0)=newTbl` |
| +4 | 记录数 | `*(DWORD*)(obj+4)=newCnt` |
| +8 | 宽（512，未动） | 方案C 只改 +12 |
| +12 | 高（128→4096） | `*(DWORD*)(obj+12)=TEX_H` |
| +16 | 字形高（24） | `if (*(DWORD*)(obj+16)!=24) continue;` |

- 布局清楚，**复制一个对象在技术上可行**
- 但要让它生效，必须让**引擎在绘制时读我们那份**——即定位并替换引擎持有的字体对象指针
- 引擎侧该指针的存放位置：本机无工具可定位（同路线 1 的阻塞）

**判定**：理论可行，静态不可达。

## 三、结论与建议

### 死结的准确表述（已从"推测"升级为"代码级证据"）

> 当前机制只有**一条**生效路径（`SetTexture` 绑定时一换），
> **没有任何还原路径**（`watchdog_swap` 死代码 + `restore_frame_end` 是空函数）。
> 于是"大图集常驻 stage0"是**结构性的**，不是时机问题；
> 任何"帧末还原/作用域还原"都必须**新写一套**，而 c44 的日志已证明
> 用 `Present` 当帧边界会第 125 帧白屏。

### 三条路线是否可继续

| 路线 | 状态 | 阻塞点 |
|---|---|---|
| 1 定位文字绘制批次 | **作废**（地址非法）→ 换方法后**受阻** | 缺 Ghidra/IDA + Java |
| 2 纹理缓存池 | 现象已实证，结构**不可静态枚举** | 需运行时日志 |
| 3 复制中文对象 | 布局已知，**定位不到持有者** | 缺工具 |

### 建议

**方案 A（推荐）**：接受保底版发版。
理由：机制只有一条路径且无还原，这与"零瑕疵无缝"结构性冲突；
唯一可行方向（per-draw 原子双改）需要先能定位绘制批次——而这一步现在做不了。

**方案 B（若仍要推进）**：装 **JDK + Ghidra**（纯只读，不动游戏文件），
对 `Obscure.exe` 建分析库，把路线 1 做完（找到文字绘制批次函数 + 字体对象持有者）。
这一步不做任何二进制修改，风险为零，且能给出"per-draw 方案是否可行"的确定答案。
预计需要 400MB 左右下载 + 一次全量分析（较慢）。
