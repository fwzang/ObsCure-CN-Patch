【要解决什么】
  现行机制在 SetTexture 命中游戏字体纹理时，立即把 stage0 换成我们的大图集。
  好处是文字立刻用新图集；副作用是「实际 stage0」与「引擎以为的 stage0」长期不一致：
    · Reset / StateBlock::Apply 会把 stage0 还原成引擎自己的小字体纹理
    · 而实测 Reset 后游戏不再调 SetTexture（其缓存失效但自己不重绑）
    · 于是 1~2 帧里文字用回原版小字（变小/乱码），
      残留的大图集也会被背景 draw 采样（竖条纹）
  现在的 Clear 黑屏是在「遮」这两个瞬间。

【本补丁做什么】
  只在绘制那一刻临时换纹理，画完立刻还原：
    DrawPrimitive 入口
      → TestCooperativeLevel（设备丢失期绝不查询，这是 c41 白屏教训）
      → GetTexture(0) 读实际 stage0（读后立即 Release，这是 c81 泄漏教训）
      → 如果 stage0 == 游戏字体纹理：SetTexture(0, 大图集) → 原 DrawPrimitive
        → SetTexture(0, 游戏字体纹理)
      → 否则：原样透传
  结果：一次绘制结束后，实际 stage0 恒等于引擎意图 —— 闪帧的物理来源被消掉。

【这是纯增量改动，不碰现有逻辑】
  未修改：SetTexture 钩子、字体指纹库、Clear 遮罩、Reset 处理、图集、字形表。
  唯一改动：vtable[81] 的钩子指针从旧 Hook_DP 换成本 cave。
  最坏情况：多 3 次 COM 调用后照原样放行，渲染结果与现在相同。

【会失去什么】
  旧 Hook_DP 里的 d2_try（EXP_D2_GATE 实验路径）不再执行。
  该路径需要环境变量开启，发行版默认关闭，实际无影响。

  【v2 修订记录 · 2026-10-26 01:47】v1 崩溃根因与修复
================================================================

v1（bf268505）实测：进游戏后黑屏不舍、每 10 秒生成一个 crash dump（共 8 个），
进程 Responding=False，已结束。

minidump 证据（analyze_dump.py 输出）
  exception : 0xC0000005   access = WRITE   target = 0x10048C64
  eip       : 0x6F57E009
  module    : version.dll   base = 0x6F1E0000   offset = +0x39E009
  file off  : 0x44E09   (= 新节 .cf10 起始 0x44E00 + 9)
  ASLR      : 重定位生效（base != 0x10000000）

结论（地址对得上，不是推测）
  · 该 DLL 在进程内被 ASLR 重定位到 0x6F1E0000
  · 既有 cave 的绝对地址之所以能用，是编译器为它们生成了 .reloc 项、加载时被修正
  · 我手写的新节没有任何重定位项，所以 0x10048C64 没被修正
  · 于是第一条 inc dword [0x10048C64] 就写向未映射低地址 -> AV
  · 挂钩点本身正确：0x6F57E000 正是 attach imm32 重定位后的 cave 入口

v2 修复
  · 入口 call $+5 / pop esi / sub esi,RVA 自取运行时基址
  · 全局访问一律 [esi+偏移]（偏移是 RVA，远小于镜像地址区间）
  · 构建器新增操作数级 PIC 自检：cave 内不得出现落在
    [0x10000000,0x11000000) 的立即数/位移 —— 实测 0 处
  · 渲染逻辑与 v1 完全一致，仅寻址方式改变

v2 静态验证
  · 84 条指令反汇编逐条符合设计，无绝对镜像地址操作数
  · 路径级栈平衡：主路径 ret 0x10 处 esp=0；11 条分支路径全部干净收尾
  · 差分白名单：原文件区仅 20 字节变化（节数/SizeOfCode/SizeOfImage/节头/attach）
  · 新增工具 02_源码/产线工具/analyze_dump.py：一条命令解析 dump ->
    异常码 + 读写方向 + 目标地址 + 模块 + 模块内偏移 + 文件偏移 + 是否 ASLR

  【v2 实测结果 · 失败，2026-10-26 01:51】结论：draw-scope 路线作废
================================================================

实测现象（用户反馈）
  · 汉字基本不显示；切屏返回同样不显示
  · 能走到「退出 / 设置」等界面时，文字是「扁扁的、无法辨认」

原因（源码有原文，不是推测）
  version_proxy.c:1027-1028
    「★ 所有『图集 512x128』的字体组（字形高 24/35/39）都要改宽高，
      否则它们的 UV 归一化仍按 512/128，采样位置错乱（表现为白条/错字）。」
  · 引擎自带的字体纹理是 512x128
  · 我们的图集是 512x4096（TEX_W=512 / TEX_H=4096）
  · 引擎用【纹理对象的 +8 宽 / +12 高】做 UV 归一化。既有机制在绑定时把 +12
    改成 4096，UV 才对得上；只换纹理指针、不改这两个字段，v = y/128 会落到
    4096 高图集的 32 倍位置 -> 采样空白区（文字消失）或纵向压缩（扁）
  · 32 = 4096/128，与「扁/不可辨」的观感完全吻合

为什么这条路走不通（结构性）
  换纹理 + 改宽高 是同一个动作的两半；而「改宽高」是写在引擎纹理对象上的
  持久副作用，没法按单次绘制做作用域还原。
  我的 draw-scope 只做了前半（换纹理），必然破坏 UV 空间。

处置
  · 已回滚到稳定保底版 V1.0（0c17dfc0），文字与黑屏均恢复正常
  · 失败件归档：_broken_v1（ASLR 崩溃）、_broken_v2（UV 错乱），禁止安装
  · 不再继续 draw-scope 方向；如需继续动底层，改走
    「hook IDirect3DStateBlock9::Apply -> Apply 之后重放参数补丁 + 重绑大图集」
    这条与实际机制同源的路线（风险中等，待评估）
