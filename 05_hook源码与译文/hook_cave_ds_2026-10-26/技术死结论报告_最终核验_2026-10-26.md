## 0. 一句话结论

`version.dll`（保底版 `0c17dfc0`）里**只有一处**会调用 `IDirect3DDevice9::SetTexture`，
且 `Hook_Present` / `Hook_Reset` **对 `g_orig_SetTexture` 零引用**。
=> **整个实现只有"绑定时替换"这一个动作，不存在任何纹理还原路径。**
"大图集常驻 stage0" 是结构性的，不是时序缺陷。

## C. `watchdog_swap` 原始机器码核验（RVA `0x6270` → file `0x5670`）

**函数头（实测字节）**
```
66 0F 6E C1            movd  xmm0, ecx              ; 参数 this 走 ECX
66 0F 6E 0D C4 19 04 10 movd xmm1, [0x100419C4]      ; g_orig_SetTexture
66 0F 62 C1            punpckldq xmm0, xmm1
66 0F 6E 0D 70 1A 04 10 movd xmm1, [0x10041A70]      ; g_bigTex
66 0F 6E 15 74 1A 04 10 movd xmm2, [0x10041A74]      ; g_fontTex
```

**门禁（实测字节）**
```
0x10006298  PXOR/PCMPEQD      ; 逐个比较 == 0
0x100062A0  MOVMSKPS EAX
0x100062A3  TEST EAX,EAX
0x100062A5  JZ  0x100062A8    ; 四者都非 0 才继续
0x100062A7  C3  RET           ; 任一为 0 -> 直接返回
```

**死分支现场（实测字节）**
```
file 0x56D2:  83 3D 74 1A 04 10 00    cmp dword [0x10041A74], 0     ; g_fontTex == 0 ?
              0F 84 02 01 00 00       jz  0x100063E1               ; -> 唯一换绑分支
```
`0x100063E1` 处才是 `SetTexture(this, 0, bigTex)` + `apply_params_fast()`。

**判定**：门禁已保证 `g_fontTex != 0`，而该分支要求 `g_fontTex == 0`
=> **该分支永不可达**；运行时 `watchdog_swap` 只做日志节流与输出。
（与 Ghidra 反编译 `decomp_out/func_10006270.txt` 一致，两路证据吻合。）

## D. "是否真的没有别的还原路径"逐个核对

方法：以 `g_orig_SetTexture`（`0x100419C4`）为锚，统计各函数内所有引用形式
（`call [abs]` / `mov reg,[abs]` / `push [abs]`）。

| 函数 | RVA / 大小 | 对 `g_orig_SetTexture` 的引用 | 说明 |
|---|---|---|---|
| `Hook_Present` | `0x32A0` / 2104 | **0（无任何形式）** | **Present 从不调用 SetTexture** → 不可能重绑/还原 |
| `Hook_Reset` | `0x2D00` / 1428 | **0（无任何形式）** | Reset 也不重绑纹理 |
| `watchdog_swap` | `0x6270` / 563 | 1 次（`0x100063EA`，**在死分支内**） | 唯一调用点不可达 |
| `Hook_SetTexture` | `0x4F20` / 2083 | 1 次（`0x10005730`） | 这是**唯一真正生效**的纹理绑定调用 |

补充事实：
- `Hook_Present` 内**直接 call** 只有 3 个目标：`0x1A60`（日志落盘）、`0x6270`（watchdog，死）、
  `0x5EB0`（`probe_state` 诊断）。**没有任何还原调用**，也没有指向裸 `ret` 空桩的调用。
- `Hook_Reset` 内未找到 `mov dword [reg+0xC], 0x80`（把高度写回 128）的立即数写。
- `Hook_SetTexture` 内 `push [0x10041A74]`（g_fontTex）只出现 1 次，且不与第二次 SetTexture 调用配对。

## E. 已确认的结论（可直接对外引用）

1. **替换只有一条路径**：`SetTexture(游戏字体纹理)` → 换成 `bigTex`。除此之外没有任何绑定动作。
2. **没有还原路径**：`Present` 零引用、`watchdog_swap` 死分支、`restore_frame_end()` 源码已空。
3. **"图集糊墙"是结构性的**：换完之后 stage0 长期等于 `bigTex`，引擎"陈旧缓存绘制"
   （不再重绑纹理的 draw）必然采样到大图集。
4. **"文字要等几秒"是同一原因**：只有等引擎第一次真正绑字体纹理，替换才发生。
5. **主程序未被修改**：`Obscure.exe` 与 vanilla 参照 SHA-256 完全一致。

| # | 疑点 | 现状 | 影响 |

## G. 若未来继续研究，正确的切入点

1. 先装 **JDK + Ghidra**，对 `Obscure.exe` 建分析库（纯只读，不改文件）。
2. 用交叉引用定位"绑字体纹理 → 绘制文字"的**同一个函数**，确认是**立即提交**还是**入队**。
3. 定位引擎持有字体对象的指针；验证"复制一份独立中文对象"是否可行（对象布局已知：
   `+0 表指针 / +4 记录数 / +8 宽 / +12 高 / +16 字形高`）。
4. **不要**再从"猜返回地址"或"手写 cave 盲打"入手——本次五轮失败已证明其代价。
