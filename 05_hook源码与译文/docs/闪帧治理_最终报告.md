## 一、现象（帧级实证，60fps 录屏）

| 指标 | 实测 |
|---|---|
| 发生率 | **100%**（每次切屏） |
| 可见时长 | **1~2 帧 = 17~33ms** |
| 结构 | `[正常菜单] → [黑屏 5~6 帧] → [闪帧 1~2 帧] → [正常菜单]`（三次事件完全一致） |
| 内容 | 上半屏/大半屏图集竖纹（bigTex 被背景类 draw 误采样），菜单文字正常 |
| 对照 | **原版（无钩子）完全不闪**（869 帧 0 事件、峰值 3.05）= 纯 swap 引入 |
| 机理 | Reset 恢复序列**最后一绑是字体** → swap → stage0=bigTex → 恢复后头 1~2 帧的背景 draw 采样 bigTex |

## 二、四条修复路线（全部终止）

### 路线 A：swap 超时恢复 / StateBlock Apply 后恢复（仅理论评估，未实施）
- **死结**：stage0 是全局槽位，文字需要它是 bigTex、背景需要它是别的纹理；钩子只能看到 `(stage,tex)` 绑定，**无法区分"这个 draw 是文字还是背景"** → "恢复成什么"在逻辑上无解
- 附带确认：**游戏确实使用 StateBlock**（CreateStateBlock ×6、3 次紧跟 Reset、EndStateBlock 恒 0 → Create+Capture 路径）；Apply 会"擦除"钩子的改动（帧 2 起自愈的机制嫌疑）

### 路线 B：StateBlock 对象 hook（3 次失败）
| 版本 | 结果 | 根因 |
|---|---|---|
| v3 | 挂死 | ① 调原函数前未 pop 游戏返回地址→参数错位 ② 收尾裸 ret 违背 callee 清栈约定（应为 ret N） |
| v4 | 崩溃 | ③ IAT 多解引用（`mov eax,[eax]` 多余一次） |
| v5 | 挂死 | ④ VirtualProtect 是 stdcall（callee 清栈），多写了 `add esp,16` |

### 路线 C：跳过 Reset 后前 N 次 Present（4 次失败）
| 版本 | 结果 | 根因 |
|---|---|---|
| v1 | 启动挂死 | base_04 初值 = **0xFFFFFFFF**（.data 初始化区），"==0"防护防错哨兵 → 误跳所有 Present |
| v2 | 白屏 | 跳过期间帧计数器不推进 → 窗口钟死锁 → 无限跳过 |
| v3 (N=12) | 闪帧泄漏 | 窗口太短（泄漏帧在 t≈0.29s） |
| v4 (N=60) | 闪帧泄漏 | **机制级缺陷**：恢复期帧率非锁定（实测均速 **1123fps**、突发 1000+）→ 60 个 Present ≈ 0.06s；要盖 0.3~1s 需 N≈300~1000，但那在稳态 60fps 下 = **冻结 5~16 秒** ✗✗ → **"按 Present 计数"的窗口在 60→1000+ fps 变化下无法标定** |

### 路线 D：Clear 遮罩（评估后未实施）
- 原理可行（Reset 后 N 帧内调 device->Clear），但**同样受"窗口标定"约束**（Present 计数在变帧率下不可靠；时间窗需 QPC=新机制），且引入 COM 调用协议风险（与路线 B 同类）
- 结论：在路线 C 暴露"帧率变化"这一机制级障碍后，D 的预期收益同样不成立

## 三、核心教训（沉淀）

1. **帧率可变环境下，任何"N 帧/N 次 Present"的窗口都不可标定**——必须用墙钟（QPC）或事件信号
2. **手写 x86 汇编钩子的调用协议**（参数骨架 / ret 清栈 / stdcall 清栈 / PIC）每一处都会致命——同项目内既有钩子是最权威的参照
3. **全局变量初值必须读文件确认**（.data 初始化区常有 0xFFFFFFFF 哨兵）
4. **Agent 侧自动化验证不可靠**（控制台抢焦点 → 游戏停渲染 + 误触 Reset）——视觉验收必须用户手动
5. **"钩子改行为"的每次扩展都要过同样的协议/逻辑双校验**（capstone + 逻辑仿真 + 加载测试，本轮已形成标准流程）
